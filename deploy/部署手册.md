# 部署 / 更新手册（服务器运维速查）

> 本文是**可复用的操作手册**：以后每次改完代码要上线，按本文对应章节走即可。
> 环境事实：项目目录 `/opt/myblog`（属 **root**），Node 22 + pm2 + Caddy，后端 `127.0.0.1:3000`，
> pm2 应用名 **`myblog-server`**，前端静态文件 `apps/web/dist`（Caddy 直接托管 + SPA 回退）。

---

## 0. 速查（最常用的三条）

```bash
# ① 日常更新：本地提交并推送（有配 GitHub Secrets 就会自动部署）
git add -A && git commit -m "feat: xxx" && git push origin main

# ② 手动部署（在服务器上，必须 root）
sudo -i && cd /opt/myblog && bash deploy/deploy.sh

# ③ 部署后看状态
pm2 status && pm2 logs myblog-server --lines 40
```

> 注意：**不要**在 `~` 或 `/root` 里敲 `pnpm install` / `pnpm build`（那里没有 `package.json`，
> corepack 会去下载一个「最新未知版本」的 pnpm，什么也不会装）。部署只跑 `bash deploy/deploy.sh`。

---

## 1. 两条部署路径

### 路径 A：推送即上线（推荐，需已配 GitHub Secrets）

1. GitHub 仓库 → Settings → Secrets and variables → Actions，确认有：
   `SSH_HOST`（服务器 IP）、`SSH_USER`（root）、`SSH_KEY`（私钥内容）。
2. 本地 `git push origin main` → Actions 会 SSH 到服务器执行 `bash /opt/myblog/deploy/deploy.sh`。
3. 进度看：GitHub → Actions → `Deploy to Server`。

> `SSH_HOST` 没配的话，工作流会**直接跳过**（只打印一段提示），此时用路径 B。

### 路径 B：登录服务器手动部署

```bash
ssh root@你的服务器IP          # 或用 admin 登录后 sudo -i
cd /opt/myblog
bash deploy/deploy.sh
```

两种路径执行的是同一个脚本、同样的结果，任选其一。

## 2. ⚠️ 一次性迁移（老服务器升级到「标签权限 + 友链 + 移动端」这一版时）

**症状**：推送后 Actions 失败 / `bash deploy/deploy.sh` 第一句就报
`Your local changes to the following files would be overwritten by merge: config/site.json`。

**原因**：老 `deploy.sh` 每次把 `deploy/runtime-config/*.json` 覆盖回 `config/`，导致服务器上的
`config/site.json`、`config/prompts/*.md` 长期处于「已修改」状态；这一版提交正好改到了这两个文件，
于是 `git pull --ff-only` 拒绝覆盖。

**处理（在服务器上，root 执行，安全）**：

```bash
sudo -i
cd /opt/myblog
cp -a config "config.bak-$(date +%Y%m%d-%H%M%S)"   # 1) 备份服务器上的现有配置
git checkout -- config/                            # 2) 清掉受控文件的本地改动
git pull --ff-only origin main                     # 3) 拿到新代码 + 新 deploy.sh（含可执行位）
bash deploy/deploy.sh                              # 4) 由新脚本接管后续部署
```

实在拉不动时（分支/浅克隆问题）：

```bash
cd /opt/myblog
git fetch origin main && git reset --hard origin/main
bash deploy/deploy.sh
```

> 为什么这样不丢数据：服务器真值在 `deploy/runtime-config/`（不受 git 影响），且新 `deploy.sh`
> 会「先快照 → 再清理 → 再 pull → 再还原」，所以 `site.json`（站点名/导航/allowedOrigins）、
> `friends.json`（友链）、`llm.json`（密钥）、`admin.json`（口令）、`prompts/*.md`（提示词）都会原样恢复。
> 这个迁移**只需要做一次**，以后都走第 3 节。

## 3. 日常更新流程（以后每次都用这套）

### 3.1 只改了代码 / 配置模板 → 推送即可

```bash
# 本地
git status                  # 确认改动范围（别把 drafts/ 个人草稿、.tmp-* 带上）
git add <具体文件>           # 或 git add -A
git commit -m "feat: 中文一句话说明(可选括号补充)"
git push origin main        # 路径 A：自动部署；路径 B：去服务器跑 deploy.sh
```

### 3.2 只改了站点内容（不用碰代码）

| 想改的东西 | 在哪改 | 生效方式 |
|---|---|---|
| 站点名 / 签名 / 导航 / 背景图 / 允许的来源 | 管理页「关于我」旁的站点设置，或 `config/site.json`（服务器上是 `deploy/runtime-config/site.json`） | 管理页保存即时生效；改文件后跑一次 `bash deploy/deploy.sh` |
| 友链 | 管理页 →「友链」标签 | 保存即时生效 |
| 自我介绍 / 时间线 / 技能 | 管理页 →「关于我」 | 保存即时生效 |
| 标签库（新建/改名/改色/删除） | 管理页 →「标签」 | 保存即时生效（AI 只能用这里的标签） |
| LLM 供应商 / Key / 限额 | 管理页 →「LLM 设置」 | 保存即时生效（Key 加密存在服务器） |
| 提示词 / Skill | 管理页 →「Skill 库」（或「LLM 设置」里的提示词） | 保存即时生效 |
| 文章、上传、图片 | 管理页 / 书架拖入 | 即时 |
| 小人开关 | 管理页 →「LLM 设置」下方小人设置 | 保存即时生效 |

> 管理页改过的 `config/*.json` 和 `config/prompts/*.md` 会在下次部署时被自动快照进
> `deploy/runtime-config/` 并原样还原，**不会被仓库版本覆盖**。

### 3.3 `deploy.sh` 到底做了什么

1. 权限自检（非 root 直接给出 `sudo -i` 提示）
2. **快照** `config/*.json` + `config/prompts/*.md` → `deploy/runtime-config/`
3. `git checkout -- config/` 清掉受控文件的本地改动（避免 pull 冲突）
4. `git pull --ff-only origin main`
5. **还原** `runtime-config/` → `config/`（服务器配置优先）
6. 站点导航补齐：有 `config/friends.json` 而 `site.json` 导航缺 `/friends` 时自动插一条「友链」（幂等）
7. 把 `config/` 回写 `runtime-config/`
8. `pnpm install --frozen-lockfile` → `pnpm build`（shared/markdown → server → web）
9. `prisma db push`（表结构同步，幂等；不改 schema 时无副作用）
10. `pm2 startOrReload deploy/ecosystem.config.cjs` + `pm2 save`

## 4. 服务器重要文件

| 路径 | 说明 | 是否入库 |
|---|---|---|
| `/opt/myblog/deploy/runtime-config/*.json` | 站点/友链/关于/LLM/小人/管理口令的**服务器真值** | ❌ 自动保留 |
| `/opt/myblog/deploy/runtime-config/prompts/*.md` | 管理页编辑过的提示词/Skill | ❌ 自动保留 |
| `/opt/myblog/data/myblog.db` | SQLite 数据库 | ❌ |
| `/opt/myblog/data/secret.key` | 加密 Key（API Key 密文依赖它，**丢了要重填所有 Key**） | ❌ |
| `/opt/myblog/uploads/{files,img,tmp,models}` | 上传文件、图片、Live2D 模型 | ❌ |
| `/opt/myblog/apps/server/.env` | 数据库连接（`DATABASE_URL`）与端口 | ❌ |
| `/opt/myblog/apps/web/dist` | 前端构建产物（Caddy 根目录） | ❌ 每次构建覆盖 |
| `/etc/caddy/Caddyfile` | 域名/HTTPS/反代配置 | ❌ |

```bash
# 后端健康

curl -s http://127.0.0.1:3000/api/site | head -c 200      # 含 "/friends" = 导航已补齐
```

- [ ] `/friends` 能打开，卡片显示站名/域名/简介，点卡片新窗口打开；底部有「交换友链」说明

## 6. 小内存服务器（1G）构建方案

**典型症状**：`bash deploy/deploy.sh` 跑到 `vite build` 就“不动了”；SSH/网页终端（阿里云 Workbench、腾讯云 OrcaTerm）报
`SocketTimeoutException` / 连接超时；日志里出现 `Killed`。原因都是**构建把 CPU/内存/IO 打满**，
`vite build` 打 1MB+ bundle（echarts / oh-my-live2d）在 1G 内存上很容易触发 OOM 或 swap 抖动，
`sshd` 来不及 accept 新连接 → 终端假死。

**方案 A（最稳，推荐 1G 机器长期用）：本地构建，只传产物**

```powershell
# 本地 D:\code.game\MyBlog
pnpm build
scp -r apps/web/dist    root@你的IP:/opt/myblog/apps/web/
scp -r apps/server/dist root@你的IP:/opt/myblog/apps/server/
```

```bash
# 服务器
cd /opt/myblog && pm2 restart myblog-server
pm2 logs myblog-server --lines 20 --nostream
```

**方案 B：加大 swap + 后台跑，不依赖终端会话**

```bash
swapoff -a 2>/dev/null; rm -f /swapfile
fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
sed -i '/\/swapfile/d' /etc/fstab && echo '/swapfile none swap sw 0 0' >> /etc/fstab
cd /opt/myblog && nohup bash deploy/deploy.sh > /root/deploy.log 2>&1 &
tail -f /root/deploy.log        # Ctrl+C 只退出查看，不中断部署
```

**方案 C：只让服务器编后端（tsc 很轻），前端用本地产物**

```bash
cd /opt/myblog
corepack pnpm --filter @myblog/shared --filter @myblog/markdown build
corepack pnpm --filter @myblog/server build
corepack pnpm --filter @myblog/server db:push
pm2 startOrReload deploy/ecosystem.config.cjs
```

**通用建议**

- 构建期间**别用网页终端盯着**，用 `nohup` + 日志，或用云厂商的「发送命令 / 云助手」（不占 22 端口会话）；
- 机器彻底连不上：控制台「重启实例」，然后直接走方案 A；
- 观察手段：`uptime`（load average）、`free -h`（swap 是否打满）、`ps aux --sort=-%cpu | head`、`dmesg | tail -20`（OOM 记录）。

## 7. 常见错误对照表

| 现象 | 原因 | 处理 |
|---|---|---|
| `Permission denied` 跑 `deploy.sh` / `cp config` | 不是 root；`/opt/myblog` 属 root（老版本脚本还没有可执行位） | `sudo -i` 后重试；`bash deploy/deploy.sh` 也可 |
| `Command "install/build" not found` | 把文档里的简写 `pnpm install/build` 当命令敲了 | 只跑 `bash deploy/deploy.sh`，它会自己 install + build |
| corepack 提示下载 `pnpm 12.x` | 在**没有 package.json 的目录**（`~`、`/root`）执行了 pnpm | `cd /opt/myblog` 再执行；新脚本已关掉该交互确认 |
| `Your local changes ... would be overwritten by merge` | 第 2 节的一次性冲突 | 按第 2 节做一次迁移（新脚本以后不会再有） |
| `git pull` 报 diverged / shallow 相关 | 服务器上的历史被改过或浅克隆 | `git fetch origin main && git reset --hard origin/main && bash deploy/deploy.sh` |
| Actions 显示成功但站点没变 | `SSH_HOST` 未配置时工作流会直接跳过 | 补 Secrets，或用路径 B 手动部署 |
| 部署时报 Prisma 下载超时 | 引擎源在国外 | 脚本默认走 `npmmirror`；仍失败可 `export PRISMA_ENGINES_MIRROR=...` 再跑 |
| 页面 200 但空白 / 刷新 `/friends` 404 | Caddy 少了 `file_server` / `try_files` | 用仓库里的 `deploy/Caddyfile.example` 重新生成后 `systemctl reload caddy` |
| 域名打不开 / 证书失败 | A 记录未解析、安全组未放 80/443、nginx 占了端口 | 检查解析与安全组；`systemctl stop nginx`（Caddy 需独占 80/443） |
| 前端请求 `CORS` 被拒 | `allowedOrigins` 没改 | 改 `deploy/runtime-config/site.json` 的 `allowedOrigins` 为 `["https://你的域名"]`，再 `bash deploy/deploy.sh` |
| 管理页一直要口令 / 改不了 | `admin.json` 丢失或口令忘记 | 重跑 `bash deploy/setup-server.sh`（会问是否重设口令），或手写 `{"password":"新口令"}` 后重启 pm2 |
| 「🤖 整理」按钮不显示 | LLM 未启用或无 API Key | 管理页 →「LLM 设置」→ 填 Key、勾启用、保存 |
| AI 整理后没打上标签 | 标签库为空 / 文章内容与标签无关 | 先去「标签」建标签；AI **只能**关联已有标签，库外名字会被忽略 |
| 图片 404 | 上传目录权限或路径不对 | 确认 `/opt/myblog/uploads/img` 存在且 pm2 以 root 运行；Caddy 的 `/uploads/*` 反代到 3000 |
| 小人加载失败 | 模型文件未上传 / 本地路径不对 | 回退到 CSS 小人属正常；上传模型见 `uploads/models/README.md` |

## 8. 回滚

```bash
cd /opt/myblog
git log --oneline -10                       # 找到上一个可用提交
git reset --hard <上一个提交>
bash deploy/deploy.sh
```

注意：回滚**代码**不会回滚数据库结构（`db push` 只增不删）与 `runtime-config/` 里的站点配置；
若改了 schema 的字段名/删除表，需要连数据库一起恢复（见第 8 节备份）。

## 9. 备份与恢复

### 9.1 部署会不会删掉我的内容？（不会，这里是边界）

一次 `deploy.sh` 只动下面这些**可再生**的东西：`git pull`（更新代码）、`config/` 的受控副本（快照 → 清理 → 还原）、
`node_modules`、`apps/*/dist` 构建产物、`pm2` 重启进程。

**永远不会被部署、git pull、构建或 pm2 重启动到的（你的内容都在这里）**：

| 数据 | 位置 | 说明 |
|---|---|---|
| 文章 / 章节 / 标签 / 分类 / 统计 / 问答历史 / 版本快照 | `data/myblog.db`（SQLite 单文件） | 被 `.gitignore` 排除，`git pull` 不碰；`prisma db push` 只加表/列，不删数据 |
| 上传的原始文件与图片 | `uploads/files/`、`uploads/img/` | 同上，git 不跟踪 |
| Live2D 模型 | `uploads/models/` | 同上 |
| 站点 / 友链 / 关于 / 小人 / LLM / 口令 配置 | `deploy/runtime-config/` | 部署时**服务器值优先**（快照→还原），不会被仓库模板覆盖 |
| 管理页编辑过的提示词 / Skill | `deploy/runtime-config/prompts/` | 同上 |
| 加密 Key | `data/secret.key` | 丢了就要重填所有 API Key → 必须备份 |
| 数据库连接 | `apps/server/.env` | 不入库，部署只在缺失时补默认值 |

**会被覆盖的是这些（都没有你的内容）**：`apps/web/dist`、`apps/server/dist`、`node_modules/`、
`config/*.json` 的工作副本（真值已在 `runtime-config/`）。

**唯一要小心的两个命令**：

- `git reset --hard origin/main` —— 只丢弃**受版本控制文件**的本地改动，不影响未跟踪文件；正常部署前脚本已自动快照，安全。
- `git clean -fd` —— **会删除未跟踪文件**，别在 `/opt/myblog` 里随手跑（它也可能删掉你自己放的文件）。
- `scp -r apps/web/dist root@IP:/opt/myblog/apps/web/` —— 只覆盖 `apps/web/dist` 目录，不要写成 `...:/opt/myblog/` 的其它路径。

**文章删除也有后悔药**：管理页/阅读页删除会写版本快照，Ctrl+Z 可撤销；AI「整理」只补摘要/标签/建议问题，
不会删文章，也不会删标签（只能关联已有标签）。

### 9.2 备份命令

```bash
# 备份（建议每天 cron，至少改动前手动一次）
cd /opt/myblog
tar czf "/root/myblog-backup-$(date +%Y%m%d-%H%M).tgz" data uploads deploy/runtime-config
```

```bash
# 恢复
cd /opt/myblog
tar xzf /root/myblog-backup-YYYYMMDD-HHMM.tgz
bash deploy/deploy.sh
```

`data/secret.key` 必须和数据库一起备份 —— 换了 key，`llm.json` 里加密的 API Key 就解不开（需要重填）。

> 想更保险可以顺手上传到别处（`rclone` / 对象存储 / 你本地 `scp` 下来），单机备份遇上磁盘故障还是会一起没。

## 10. 本地自检（推之前跑一遍更稳）

```bash
pnpm --filter @myblog/shared build                 # 共享类型（server/web 都依赖）
pnpm --filter @myblog/server exec tsc --noEmit -p apps/server/tsconfig.json
pnpm --filter @myblog/web build                    # 前端构建
pnpm dev                                           # 本地：前端 5173，后端 3000
```

服务器脚本改过之后，建议本地先 `bash -n deploy/deploy.sh` 做语法检查。
